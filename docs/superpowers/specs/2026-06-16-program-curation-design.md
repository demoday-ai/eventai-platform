# Дизайн: радикальное улучшение подбора персональной программы

Дата: 2026-06-16
Статус: design (одобрен к реализации после ревью)

## Context

Подбор персональной программы — ядро ценности EventAI (найти «свои» проекты среди ~330 и не утонуть). UX-тесты 5 персон показали, что именно это звено слабое и подрывает доверие:

- «Если успеете» = почти весь каталог (13-16 из 15) — селективности нет, обещание «узкая подборка» не выполняется.
- Программа-кнопка противоречит советам агента в чате.
- Явные негативы игнорируются («таможня не интересна» → таможня снова в программе).
- Нельзя поправить подборку; `/rebuild` сносит профиль; программа не отсортирована по времени, конфликты слотов не показаны.

Концепт был прогнан через панель из 4 челлендж-агентов (IR-исследователь, staff-инженер, продакт/UX, минималист). Вывод панели: первоначальный концепт переусложнён ~вдвое — половину он переизобретает поверх существующего кода. Этот дизайн — изящный консенсус: переиспользуем то, что есть, добавляем минимум, без миграций БД.

## Цель / Не-цель

**Цель:** программа становится узкой и релевантной; чат и кнопка показывают одно и то же; негатив уважается; подборку можно править репликами без зависания бота; время и конфликты слотов видны.

**Не-цель (этот заход):** гибридный ретрив (vector+BM25), новые поля/таблицы БД, ручной pin как поле БД, «острый вопрос» в онбординге, awareness «день идёт сейчас». См. «Отложено».

## Что уже есть (переиспользуем, не трогаем структуру)

- **Единый источник правды уже единый:** и кнопка «Моя программа», и системный промпт чата читают одну таблицу `Recommendation`. «Две головы» — НЕ от двух хранилищ.
- `category` = `must_visit` / `if_time` уже существует (не вводим новый «tier»).
- `_llm_rerank` (listwise-подобный) и `generate_recommendations` + `format_program` уже есть.
- `cmd_recommend` (`global_cmds.py`) — уже пересборка с сохранением профиля (ядро для рефайна).
- `GuestProfile.nl_summary` — свободный текст профиля, уже уходит в `profile_text` для rerank → **сюда кладём негатив, без миграции**.

## Откуда реально «две головы»

Промпт агента (`prompts/agent.py`) разрешает советовать в обход замороженной таблицы, нигде не учитывает негатив и советует `/rebuild` (который сносит профиль). Проблема в инструкциях и селективности, а не в данных.

## Дизайн (5 изменений + UX-полировка)

### 1. Селективность через градацию (главный выигрыш)
`_llm_rerank` отдаёт по каждому проекту градацию **strong / weak / off** (вместо `relevant: true/false`) + короткую причину. Тиры собираются **детерминированно** (не LLM):
- `off` → не показываем (drop);
- `strong` → `must_visit` (основа), потолок ~8, защита от пустоты `min 3`;
- `weak` → `if_time` (короткий хвост ~5), остальное скрыто.

Чинит «весь каталог в если-успеете» и фиктивный порог `0.6*top` (он сейчас по позиции, а не по релевантности — `_schedule_rerank` перетирает score позиционным `100-pos`). Остаётся **один** LLM-вызов на сборку.

### 2. Учёт негатива
- Негатив гостя пишется в `nl_summary` строкой «Не интересует: …» (уже попадает в `profile_text`).
- В системный промпт `_llm_rerank` — правило: проекты из стоп-листа → `off`.
- Хранение — существующее поле, без миграции. (Жёсткий pre-filter по тегам — в «Отложено»; для v1 достаточно стоп-листа в промпте + персиста в профиле, что делает применение стабильным между пересборками.)

### 3. Правки из чата без латентной ловушки
`refine` как один агент-тул = до 3 LLM-вызовов в ходе (50-80с) → таймаут. Поэтому **два инструмента по цене**:

- `update_program(remove: list[int] = [], add: list[int] = [], exclude: list[str] = [])` — **мгновенно, без LLM**: меняет сохранённую таблицу `Recommendation` и дописывает негатив в `nl_summary`. `remove` — номера из текущей программы; `add` — номера проектов из каталога события (резолвятся против каталога, добавляются в `must_visit`); `exclude` — темы/теги в стоп-лист. Покрывает частый случай («убери таможню», «добавь проект 5»).
- `rebuild_program(note: str)` — **редкий путь, 1 LLM-вызов**: дописывает `note` в `nl_summary` и вызывает существующую `generate_recommendations` (как `cmd_recommend`). Для смены интересов («больше про RAG»).

Решение по латентности: тяжёлый путь (rebuild) редкий; частые правки (update_program) мгновенные. Это уводит от 3-вызовной ловушки на горячем пути.

### 4. Чат и программа — одно и то же, но чат не нем
- Промпт: агент **не выдаёт порядок/состав, противоречащий сохранённой программе**; «поменять подборку» → вызвать `update_program`/`rebuild_program`, НЕ писать `/rebuild` и не переранжировать текстом.
- Свободный совет остаётся («не твой стек, но команда сильная — сходи», предупреждения о конфликтах). Единый источник = единый порядок и состав, не кляп.
- Убрать из промпта совет про `/rebuild` (стр ~61).

### 5. UX-полировка (дёшево, высокий эффект)
- **Сворачивать, а не прятать:** «Твой день» (must) + свёрнутое «Стоит заглянуть» (if_time) + **«Весь каталог» доступен всегда** (кнопка) — убирает тревогу «алгоритм спрятал моё».
- **Сортировка must по времени** + пометка конфликтов слотов: «в 14:15 два под тебя — какой ставим?».
- **Причина по шаблону «грань профиля → проект + время»**: «просил RAG в проде — у них RAG на 2М докум, зал 3, 14:15». Нет конкретной грани → не в основу. (Причина = поле `Recommendation.llm_summary`, уже существует.)
- **Diff + undo** на правку: «убрал таможню, поднял RAG чтобы не было дыры [Отменить]».
- **Убрать `#`** — везде только номера (показ + промпты).
- Тиры назвать по-человечески: «Основа дня» / «Если будет окно».

### 6. /rebuild чинится
`/rebuild` больше не сносит профиль — становится пересборкой с сохранением (как `rebuild_program`/`cmd_recommend`). Снос профиля — только по явному «начать заново».

## Данные

Без миграций. Используем:
- `GuestProfile.nl_summary` — негатив строкой.
- `Recommendation.category` (must_visit/if_time), `.llm_summary` (причина), `.rank`, `.slot_id`, `.visit_order` — уже есть.

## Надёжность (обязательно)

- Битый/обрезанный/пустой JSON градации → фолбэк на векторный порядок (как сейчас при ошибке rerank). Программа **никогда не пустая**.
- `rebuild_program` вернул пусто → не перетираем рабочую программу, говорим «не нашёл изменений».
- Защита от пустоты must: `min 3` (показать ближайшее с честной пометкой).

## Отложено (позолота / под замер)

- **Гибридный ретрив** (vector ∪ BM25 ∪ теги через RRF) против «дыры recall» при сжатых Gemini-косинусах. Сначала **замерить**: прогнать 10-15 профилей, сколько релевантного не попадает в vector-top-40. Если recall высокий — не трогаем; дырявый — первый приоритет следующего захода.
- pins как поле БД (вместо этого — мгновенный `update_program`).
- «Острый вопрос» в онбординге, awareness текущего времени.

## Проверка end-to-end

- TDD на каждое изменение: градация→тиры (селективность), негатив→off, update_program мгновенно меняет таблицу, rebuild_program переиспользует generate_recommendations, фолбэк на мусор.
- Прогон в CI bot-джобе (Postgres pgvector); Docker локально выключен.
- Живой прогон через `botcli` на проде: «убери таможню» (мгновенно, исчезает и из программы), «больше про RAG» (пересборка с ack), проверка что «если успеете» стал коротким, конфликты слотов показаны.

## Риски

- LLM-негатив нестабилен — смягчаем персистом стоп-листа в профиль (применяется каждую пересборку одинаково).
- Латентность rebuild (~20-30с) — редкий путь + мгновенный ack «Пересобираю…».
- Стабильность listwise-градации между пересборками — `update_program` (частый путь) детерминирован и не трогает остальное; rebuild меняет всё осознанно.
